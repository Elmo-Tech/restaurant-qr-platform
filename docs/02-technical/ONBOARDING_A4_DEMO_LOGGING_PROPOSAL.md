# A4 release follow-up — private Demo URL logging

**Review only. Production gate open.** This proposal does not change Demo link format, session exchange, expiry, onboarding history, or the Platform import route. A link works repeatedly until the Demo ends, so treat its path as a credential (see [Demo Restaurants](../01-domain/DEMO_RESTAURANTS_SPEC.md#3-life-of-a-demo) and [A4 validation](ONBOARDING_A4_VALIDATION.md)). This branch contains only this document, based on #79 at `6437d43`; the candidate and focused probes described here remain in the local `onboarding-a4-release-hardening` worktree and are not part of #79 or this branch.

## Findings and candidate mitigations

| Layer | Evidence and candidate mitigation |
| --- | --- |
| Coolify HTTPS proxy and any preceding hop | The [deployment runbook](COOLIFY_DEPLOYMENT.md) puts Traefik or Caddy in front of Nginx. Effective router configuration, enabled diagnostics, and sinks were not inspected. A downstream change cannot sanitize logs already written by an earlier hop. |
| Nginx Gateway | The local image has two HTTP-scope access log directives before mitigation: the [Gateway template](../../infra/docker/nginx/gateway.conf.template) logs normalized `$uri` (including the Demo path segment), and the base image's `main` format logs the raw request target and Referer. The local candidate removes the duplicate base directive and logs a fixed `/demo/[redacted]` path across vhosts, retaining method, host, status, bytes, duration and request ID. Error logging is independent of `log_format`; the candidate drops built-in error details only in the matched Demo location of each frontend vhost. Pre-location, default/redirect-vhost and debug diagnostics are not covered by that location rule. |
| Next.js Web (16.4.2) | The local candidate suppresses matching dev request lines without suppressing unrelated logs and sets Demo-only `Referrer-Policy: no-referrer` to avoid forwarding the capability as a browser Referer. This header cannot scrub already-received headers or browser history, and request-line suppression is not a trace or exception sanitizer. **Local `next dev` still wrote the inert marker to `.next/dev/trace`.** Do not use working links in development. Loopback `next build`/`next start` did not show the marker in the inspected terminal output or `.next/trace` for successful document and RSC requests; this was neither the production standalone image nor an exhaustive failure test. |
| Nest API and Platform console | The exchange is `POST /api/v1/demo/enter` with the capability in the body. The existing [request context middleware](../../apps/api/src/common/http/request-context.middleware.ts) logs the matched route template, method, status, duration and request ID, without capturing query strings, bodies, cookies, Authorization or Referer. The focused test used the actual controller with a stub service. It does not establish safety for real issuance responses, unexpected exceptions, Platform Web, client telemetry, or collector-side enrichment. |

## Redacted local evidence

Only loopback and inert synthetic markers were used. No working links or raw log excerpts are included. Gateway logs were attached in memory with Docker's `none` log driver. Next output was captured in memory and Next artifacts were inspected and removed with the disposable app copy; no local `.env` files were loaded into that copy.

- **Nginx:** `DOCKER_BUILDKIT=0 fnm exec --using=24.15.0 node tests/release/onboarding-a4-gateway-demo-logging.mjs` from the local candidate worktree. Builds with cached `nginx:1.28-alpine` and `node:24.15.0-alpine`; `nginx -t` passed. The earlier probe covered Web 200/502, wildcard 502, Platform 200/502, legacy 308, unknown host 444 and a normalized path. A release follow-up reran the focused Gateway probe and confirmed access redaction, matched Web/Platform upstream error suppression and ordinary-route logging. Neither captured stream contained the marker on those probes. `/demo-credits` logged exactly once; an unrelated upstream 502 retained stderr diagnostics.
- **Next:** Prior candidate evidence used `fnm exec --using=24.15.0 node tests/release/onboarding-a4-web-demo-logging.mjs`, then the same command with `--production`. Both modes passed the document/RSC console and Referrer-Policy probes, with `/demo-credits` as the ordinary-route control. The dev trace did contain the marker; the inspected production-mode trace did not.
- **Nest:** Prior candidate evidence used `fnm exec --using=24.15.0 npm exec --workspace=apps/api -- jest --runInBand src/demo/demo-logging.spec.ts src/common/http/request-context.middleware.spec.ts` (15 tests passed). The 404 rejection and 400 validation produced correlated route logs with no marker in captured log, warn or error calls. No API code change was needed for those paths. This is not full-app or database validation.

## Production acceptance — deployment owner sign-off required

1. Inventory every effective hop and sink for Demo traffic, including HTTP-to-HTTPS and legacy/default routes, CDN/WAF if present, the Coolify proxy, Nginx, standalone Next Web and Platform, and Nest. Verify active access/error/debug logging, scrape/forwarding, exception reporting, APM/tracing, analytics, and diagnostics policies against the exact deployed versions and settings. Omit the raw URL, Referer, cookies, Authorization, and Demo request/response payloads **before capture**, not just at the final sink. Preserve safe route labels, request IDs, status and timing. Do not globally disable logging.
2. With explicit operational approval, verify the deployed configuration and artifacts through the effective ingress and every sink using inert synthetic markers only. Exercise document/RSC, redirect/default-host, rejection/validation, upstream failure/timeout, and application exception paths; include issuance and exchange body/response capture controls in an approved production-equivalent environment. Match on an independent request ID, prove each sink received its expected control events, and have the owner check for the marker at capture and after shipping. Record only sanitized counts/statuses, artifact identifiers, and owner sign-off. A missing log event, an unverified sink, or a local-only run is not a pass. Prefer route-scoped suppression/redaction; if the edge cannot exclude the capability before capture, keep DEMO gated and return for approval of a safer link transport.
3. Assess historical log exposure, access and retention under the existing incident process. Treat older access logs as potentially sensitive and assess invalidation of any affected still-active links. Do not copy raw URLs, markers or log exports into tickets, this repository, or release evidence.
